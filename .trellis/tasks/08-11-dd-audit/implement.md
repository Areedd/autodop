# DD01–DD04 实现完整度核对 — 执行计划

## 执行模式

主会话编排 + 4 个并行 `trellis-research` 子代理（每文档一个，派发 prompt 以 `Active task: .trellis/tasks/08-11-dd-audit` 开头），子代理产出各文档的核对矩阵（草稿，写入任务目录 `audit_parts/`），主会话合并、补查、写最终报告。

## 步骤清单

- [ ] **S1 派发前准备**：抽取每文档条目清单（ID 化）写入 `audit_parts/` 骨架；向子代理提供检索边界（design.md §4）与判定标准（design.md §3）。
- [ ] **S2 并行派发 4 个子代理**（trellis-research，每文档一个）：
  - DD01：核对 §3 总体方案（3.1 设计原则量化约束、3.2 架构三层与三条数据流、3.3 模块要点、3.4 端到端流程、3.5 技术选型落地）；§1.3 三条研究目标；§2/§4/§5 标 N/A。
  - DD02：核对 §1.3 功能需求（输入/输出/用途/训练触发）、§2 总体设计（预估流程五环节、模块划分）、§3 特征设计（特征清单逐项、两类边）、§4 模型结构与训练数据生产、§5 接口与产物格式、§6 评估指标/代码结构/测试设计。
  - DD03：核对 §1.3、§2（决策窗口）、§3（搜索/蒸馏/标签）、§4（在线决策/负载修正/安装）、§5（执行流程/决策接口/负载采集/产物格式）、§6（评估指标/代码结构/测试）。
  - DD04：核对 §1.3、§2（增量位置/调整流程/模块）、§3（节点资源感知）、§4（调整对象与规则/衔接）、§5（执行/资源接口/配置项）、§6（评估/代码结构/测试）。
- [ ] **S3 合并与补查**：主会话逐条复核子代理产出；对可疑判定直接查代码确认（重点：DD02 排序模型/特征/图编码实际形态 vs 文档 GAT 描述；DD03 决策窗口实际插入点；DD04 资源视图归一化按容量 vs 实现；轨迹三阶段字段；负载修正死区/下限常量）。
- [ ] **S4 效果证据收集**：从 13 份报告 + runs/ + journal 提取量化指标（搜索质量、决策质量对比、修正效果、实例差异化、决策耗时、排序准确率等），标注来源与置信度。
- [ ] **S5 写报告**：`tools/autodop/IMPLEMENTATION_AUDIT_REPORT.md`（结构见 design.md §5）。
- [ ] **S6 自检（trellis-check 或主会话复核）**：抽查 10 条判定复核（AC4）；验证每条 ❌/🟡 有检索范围说明、每条 ✅ 有证据；报告与 PRD 的 AC1–AC4 逐条对表。
- [ ] **S7 提交**：报告 + 任务工件提交（commit message 前缀 `docs:`）。

## 风险与回滚

- 风险 1：子代理判定与代码不符 → S3 主会话逐条复核 + 抽查；必要时重派单个文档。
- 风险 2：效果证据分散、报告内数值互相矛盾 → S4 以最新报告/runs 为准，矛盾处并列标注并说明。
- 回滚点：报告为独立新文件，不修改产品代码；任何一步出错可安全重跑对应步骤。
