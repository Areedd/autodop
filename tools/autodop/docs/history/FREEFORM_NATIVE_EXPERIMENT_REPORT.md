# Native free-form AutoDOP experiment report

Date: 2026-07-23

## Outcome

The new generator produces shorter and materially more varied SQL, but the
30% performance claim does **not** hold on a correctly loaded standard TPC-DS
SF10 dataset.

- The final unrestricted generation run contains 100 SQLs, 80 distinct
  normalized physical-plan fingerprints, and 41 output topologies. Query
  length is 24--38 lines (median 30), and join count is 5--11 (median 8).
- On the corrected `tpcds_sf10_native` database, 0/56 queries passed the rule
  that fragment AutoDOP must beat every fixed global DOP (1/2/4/8) by at least
  30% on mean, median, P90, and P99.
- Across the 56 exploratory runs, per-query minimum improvement ranged from
  -9.260% to +7.452% (median -1.439%, mean -1.508%).

The earlier 30%+ result is invalid for performance claims because the original
fact tables were loaded with shifted columns. The artifacts are retained as
negative evidence and now carry an explicit invalidity marker.

## Data-integrity finding

The existing `tpcds_sf10` and `tpcds_sf100` fact-table DDLs move item/order key
columns to the front, but their Stream Load scripts did not specify the source
`.dat` column order. For example, the standard `store_sales.dat` starts with
`ss_sold_date_sk`, while the deployed table starts with `ss_item_sk`.

Consequences in the old database included:

- `store_sales.ss_sold_date_sk` ranged from 1 to 102000/204000 instead of the
  standard date surrogate-key range around 2450816.
- `store_sales JOIN date_dim` returned no rows for the generated predicates.
- Catalog and web facts were also shifted; some date columns happened to hold
  other date-valued fields, which concealed the corruption.

The isolated database `tpcds_sf10_native` was therefore created from the same
dsdgen SF10 files with explicit standard column mappings. No original database
or table was removed. Loaded rows and sold-date ranges are:

| table | loaded rows | sold-date range |
|---|---:|---:|
| store_sales | 28,800,991 | 2450816--2452642 |
| catalog_sales | 14,401,261 | 2450815--2452653 |
| web_sales | 7,197,566 | 2450816--2452642 |

All three tables join `date_dim` over month sequences 1176--1236. Unmatched
rows are the nullable dates generated by TPC-DS.

## New generation method

The generator separates the SQL into independently composable dimensions:

1. Native channel sources: store, catalog, and web sales joined to `date_dim`,
   optionally through a native business dimension such as `customer`.
2. Entity/period keys: surrogate or business entity keys at day/month/week
   grain.
3. Set relationships: channel exclusion and overlap with independently chosen
   channel arity and time window.
4. Result topology: scalar KPI, UNION/UNION DISTINCT, grouped metrics, pivot,
   Top-N, period rollup, window rank/share, full-outer period comparison,
   GROUPING SETS, and nested aggregations.
5. Presentation modifiers: ordering, limiting, windowing, re-aggregation, and
   joining are composed without duplicating the expensive source branches.

This is more varied than the previous fixed audit/anchor envelope. It also
keeps individual SQLs short. The generator is deterministic and records SQL
hashes, grammar choices, complexity, and development/holdout labels.

The generator does not claim that 80 physical plans represent 80 independent
performance mechanisms. They share set-processing cores; the 80 count measures
plan diversity only.

## Valid performance evidence

### Fixed-DOP motif curves

All expensive native motifs preferred DOP4 or DOP8 on corrected SF10:

| motif | DOP1 | DOP2 | DOP4 | DOP8 | best |
|---|---:|---:|---:|---:|---:|
| EXCEPT channel set | 204.7 | 148.5 | 123.2 | 123.0 | 8 |
| anti join | 209.0 | 161.6 | 142.0 | 152.4 | 4 |
| conditional aggregate | 365.1 | 229.3 | 171.0 | 160.0 | 8 |
| NOT EXISTS | 493.8 | 276.0 | 175.3 | 141.5 | 8 |
| INTERSECT channel set | 107.9 | 93.7 | 85.1 | 89.8 | 4 |
| customer-item aggregate | 751.5 | 416.4 | 250.8 | 186.7 | 8 |
| row-level running window | 353.0 | 247.5 | 170.9 | 151.3 | 8 |
| row-level LAG | 355.5 | 247.7 | 181.6 | 158.6 | 8 |
| NTILE distribution | 364.2 | 269.3 | 206.0 | 177.7 | 8 |
| one-million-row Top-N | 260.1 | 146.5 | 106.2 | 115.3 | 4 |

Values are median milliseconds after one warmup, with three measured runs per
DOP. No expensive motif with a strong DOP1 preference was found.

### Cost-aware fragment policy

The operator-specific policy incorrectly set the complete EXCEPT input subtree,
including large fact scans, to DOP1. A general cost-aware policy was added:

- DOP4 for fragments with cost at least 10,000,000 or at least 16 scan ranges.
- DOP1 for lightweight fragments.

It accepts arbitrary plan structures and does not fail merely because a named
operator is absent. On the shortest representative query (three repetitions):

| mode | mean | median | P90 | P99 |
|---|---:|---:|---:|---:|
| fragment cost-aware | 210.948 | 209.610 | 213.517 | 214.396 |
| global DOP1 | 272.424 | 265.578 | 282.859 | 286.747 |
| global DOP2 | 210.210 | 206.026 | 223.270 | 227.150 |
| global DOP4 | 198.112 | 197.009 | 201.917 | 203.021 |
| global DOP8 | 211.385 | 208.550 | 215.624 | 217.216 |

The new policy removes the large regression of the old policy, but remains
6.479% slower than global DOP4 on the worst comparison statistic.

### Full 56-plan screen

With the cost-aware policy on corrected SF10:

- Passed at 30%: 0/56.
- Best per-query minimum improvement: +7.452%.
- Median per-query minimum improvement: -1.439%.
- Best median-latency mode counts: global DOP4=23, fragment=17, global DOP8=10,
  global DOP2=6.

The fragment policy can win individual median measurements, but not by 30%
against all fixed DOPs and all requested tail statistics.

### Concurrency boundary

The AutoDOP HTTP server's accept backlog was increased from the Python default
of 5 to 128; this fixes concurrent decision failures without changing policy
or adding a fallback. The FE decision timeout was set to 1000 ms.

| concurrency | best global DOP | best-global makespan | fragment makespan | fragment vs best |
|---:|---:|---:|---:|---:|
| 4 | 4 | 769.445 ms | 807.102 ms | -4.894% |
| 16 | 4 | 3007.587 ms | 3123.030 ms | -3.838% |
| 32 | 4 | 5983.709 ms | 6256.809 ms | -4.564% |

Concurrency 64 was excluded: the fixed DOP8 phase exceeded a BE process memory
limit at about 12.37 GB. An OOM is not counted as a performance win.

## Why the 30% target is unsupported here

Fragment-level DOP can materially beat every fixed global DOP only when a query
contains expensive fragments with strongly conflicting DOP optima. Corrected
SF10 does not provide that conflict for the tested grammar:

- Large scans, set operations, joins, aggregates, and global windows all prefer
  DOP4 or DOP8.
- Lightweight root/finalize/dimension fragments benefit from DOP1, but their
  contribution to end-to-end latency is too small to create a 30% gain.
- More outer SQL topologies change the physical plan but not the dominant scan
  and shuffle cost.
- Up to safe concurrency 32, global DOP4 remains best. At concurrency 64 the
  experiment becomes memory-invalid before a meaningful comparison completes.

Therefore, retaining a 30% claim would require either malformed/custom data,
an intentionally inflated query envelope, or a different engine/workload where
real fragment optima conflict. None should be hidden as ordinary SQL diversity.

## Reproduction

```bash
# Create the isolated, correctly mapped SF10 subset.
tools/autodop/setup_tpcds_sf10_native.sh

# Generate the free-form and inverse-scaling probes.
python3 tools/autodop/generate_freeform_sql_suite.py \
  --output-dir tools/autodop/queries/freeform_native_sf10_100 \
  --count 100 --search-space freeform_matrix --database tpcds_sf10_native \
  --max-lines 45 --max-joins 11
python3 tools/autodop/generate_inverse_motif_probe.py \
  --output-dir tools/autodop/queries/freeform_native_sf10_inverse --force

# Profile fixed DOP curves independently from AutoDOP.
python3 tools/autodop/profile_fixed_dop_suite.py \
  --manifest tools/autodop/queries/freeform_native_sf10_motifs/manifest.json \
  --database tpcds_sf10_native --warmup-rounds 1 --repetitions 3 \
  --output tools/autodop/runs/freeform_native_sf10/motif_fixed_dop_3x.json

# Start the general fragment-cost policy (in a separate terminal).
python3 tools/autodop/autodop_server.py \
  --host 127.0.0.1 --port 18080 --cost-aware \
  --low-dop 1 --high-dop 4 \
  --high-fragment-cost 10000000 --high-scan-ranges 16

# Screen the 56 distinct plans with the cost-aware service running.
python3 tools/autodop/screen_structural_query_suite.py \
  --manifest tools/autodop/queries/freeform_certified_final_v2/manifest.json \
  --database tpcds_sf10_native --repetitions 1 \
  --minimum-improvement-pct 30 \
  --output tools/autodop/runs/freeform_native_sf10/freeform_56_cost_aware_round1.json
```

## Recommended next experiment

Use complete, correctly mapped TPC-DS/TPCH/SSB databases and profile official
queries before generating synthetic combinations. Train or search a policy on
development query templates, then freeze it and evaluate unseen templates and
time windows. The acceptance rule should remain unchanged. A 30% target should
be treated as a hypothesis, not a generator constraint.
