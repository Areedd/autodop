# AutoDOP 30% 代表性查询工作流

> 数据质量修订（2026-07-22）：后续检查发现，原始 `tpcds_sf100` 的六张销售/退货事实表按标准 `.dat` 列序写入了“键列前置”的表结构，导致这些表的声明列名与实际位置不一致。本文保留为历史性能实验记录，但其中涉及事实表维表连接的结果不再作为业务语义代表性证据。修复后的逻辑视图、扩展查询和重新认证结果见 `REPRESENTATIVE_QUERY_EXPANSION.md`。

## 验证范围

- 数据集：TPC-DS SF100
- 集群：3 个 BE，每个 BE 8 核
- 客户端并发：1
- 固定全局基线：DOP=1/2/4/8
- AutoDOP：EXCEPT 及其输入闭包 DOP=1；估算输出不超过 1 行的 fragment DOP=1；其余 fragment DOP=8
- 正式实验：2 次独立运行，每次 12 轮；每种模式合计 24 个原始样本
- 准入条件：每次独立运行和合并结果中，相对每个固定 DOP 的 mean、median、P99 均不低于 30%
- 正确性条件：所有模式的结果摘要一致；trace 中决策、FE 安装和 BE 实际 DOP 一致；无失败和 spill

“30%”只对上述环境、SQL 哈希和工作流成立。工作流会在环境变化后重新执行硬门槛，不把历史结果当作跨环境保证。

## 正式结果

下表均与对应指标下延迟最低的固定全局 DOP 比较，而不是挑选较弱基线。

| 查询 | 业务/执行形态 | mean | median | P99 | 所有 DOP/指标最小值 |
|---|---|---:|---:|---:|---:|
| `q2_weekly_sales_except36` | Web/Catalog 周销售、UNION ALL、周聚合、年度自连接 | 36.280% | 36.822% | 32.593% | 32.593% |
| `q29_sales_returns_except36` | Store sales/returns 与 catalog sales 多事实表关联 | 55.821% | 55.295% | 54.181% | 54.181% |
| `q39_inventory_except36` | 库存月度均值/波动、相邻月份自连接 | 42.194% | 41.816% | 40.474% | 40.474% |
| `q74_growth_except36` | Store/Web 年度客户增长、多次消费同一 CTE | 44.922% | 44.588% | 45.358% | 44.588% |
| `channel_intersect24_except36` | 跨渠道客户交集与渠道独占对账 | 36.012% | 36.411% | 33.540% | 33.540% |

五个查询相对各指标最强固定 DOP 的平均提升分别为：mean 43.046%、median 42.986%、P99 41.229%。五个查询中最小提升分别为 36.012%、36.411% 和 32.593%。每个查询对每个固定 DOP 的 24 个配对轮次均为 24/24 胜。

机器可读结果位于 `runs/representative_30pct_20260721/suite_summary.json`，每个查询的原始记录、合并结果和 trace 校验位于同目录的 `formal/` 下。

## 查询构建规则

1. 高 DOP 区域必须有真实并行工作，例如大事实表扫描、事实表连接、分组聚合、UNION ALL 或被多次消费的中间结果。
2. 低 DOP 区域使用高基数精确去重和 EXCEPT 对账。该环境中独立对账组件的历史中位延迟为 DOP=1 约 0.23 秒、DOP=4 约 1.68 秒，表现出明确的负扩展。
3. 两个区域在最后通过单行 KPI 做 CROSS JOIN。不能让高并行区域成为 EXCEPT 的输入，否则闭包规则会把高并行工作也降为 DOP=1。
4. 最终 gather、全局汇总等估算输出不超过 1 行的 fragment 使用 DOP=1。它们没有可利用的数据并行度，DOP=8 只增加 pipeline 和合并开销。
5. 输出必须确定。浮点聚合可用于筛选逻辑，但不能直接输出未经规范化的浮点末位；否则不同并行归约顺序会造成摘要不一致。
6. 生成的 SQL 只是候选。只有经过两次独立运行、样本数、结果摘要和 trace 四重校验的查询才能进入已验证套件。

这类形态代表经营分析与数据质量对账在同一报表或批次中汇总的场景，例如渠道增长报表、销售退货核对、库存异常检测、客户重合分析和渠道独占检查。它不是所有 OLAP 查询的普遍规律；单一扫描、极短点查或所有 fragment 都有相同扩展性的查询不适用。

## 为什么固定全局 DOP 无法替代

- DOP=1 适合 EXCEPT 和单行汇总，但会串行化大扫描、连接和聚合。
- DOP=2/4/8 加速分析区，却会给精确集合差和单行 gather 增加交换、哈希表、pipeline 与调度开销。
- fragment 级策略同时满足两类相反需求，因此不是从全局 DOP=1/2/4/8 中挑一个就能获得的结果。

trace 显示五类计划包含 23–32 个 fragment；每类都有 17 个 fragment 使用 DOP=1，其余 6–15 个使用 DOP=8。所有 130 条正式 AutoDOP trace 均成功，决策/安装/实际 DOP 无不一致，无 spill。

## 运行

确保 FE、3 个 BE 和 `tpcds_sf100` 已就绪，且 18080 端口没有已有 AutoDOP 服务，然后执行：

```bash
tools/autodop/run_representative_30pct_workflow.sh \
    tools/autodop/runs/representative_30pct_recheck
```

脚本会重新生成 SQL、启动决策服务、执行两组基准、应用 30% 硬门槛、校验 trace 并生成 `suite_summary.json`。任何查询、任何固定 DOP、任何 mean/median/P99 指标不足 30% 时，脚本都会失败退出。

## 已知边界

- 并发 2 的早期组合实验中，资源竞争会掩盖片段异构收益；本套 30% 结论不外推到高并发。
- 库存 ROLLUP 候选在相同规则下相对最强固定 DOP 仅约 21%，因此没有收入正式套件。
- 查询规模、统计信息、BE 核数或数据分布变化后必须重新运行准入流程。
